How to read a card

Filled dot — always present on every doc.

Open ring — optional; absent, not just empty, until set.

ƒ

ƒ mark — derived client-side and persisted, like a formula field written back to the record rather than recalculated on read.

Doc-ID chip — two strategies are in play: auto means Firestore assigns a random ID (addDoc); anything else is a deterministic key the app builds itself (setDoc), so writes to the same logical entity always land on the same doc.

The daily count sheet — one row per product, rolled up per section, per calendar day.

fieldtypenotes

Worth knowing before you query any of this

  • Login access isn't in the database at all. The allow-list lives in code (lib/allowedEmails.ts), not Firestore — there's no users collection to check.
  • Nothing here is a real foreign key. Firestore has no join/referential-integrity concept, so ids like customerId or pricebookId are trusted, app-maintained pointers — a stale one won't be caught by the database itself.
  • category is intentionally open-ended. Sales, Purchases, Inventory, and Refunds all derive their sections from whatever categories currently exist in products, rather than a hardcoded list — the fix for a recurring class of bug where a new category quietly disappeared from one screen but not another.
